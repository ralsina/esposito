# App Loading Mechanism

Esposito runs apps compiled as standalone ELF binaries, loaded dynamically from the SD card at runtime. This document explains the full pipeline from compilation to execution.

## Overview

```
  +-----------+     +----------+     +--------------+
  | app.c     | --> | app.elf  | --> | /sdcard/apps/ |
  | libs/ui2/ |     | (PIE)    |     | <name>/      |
  +-----------+     +----------+     |   program.elf |
                                     |   manifest.cfg|
                                     +--------------+
                                          |
                                          v
                                   +--------------+
                                   | elf_loader   |
                                   | parse,       |
                                   | relocate,    |
                                   | mmap flash   |
                                   +--------------+
                                          |
                                          v
                                   +--------------+
                                   | app_heap     |
                                   | (96KB DRAM   |
                                   |  per app)    |
                                   +--------------+
                                          |
                                          v
                                   +--------------+
                                   | os_core      |
                                   | event loop   |
                                   | dispatch     |
                                   +--------------+
```

Apps are compiled to relocatable ELF binaries (`program.elf`) on the development machine, copied to the SD card, then parsed and relocated at runtime by the firmware's ELF loader before execution.

---

## Compilation

Each app is compiled by `scripts/build_app.sh` using the Xtensa cross-compiler:

```
xtensa-esp32-elf-gcc \
    -nostdlib -nostartfiles -ffreestanding \
    -mlongcalls -Wl,--emit-relocs \
    -T apps/<name>/app.ld      # or apps/app_template/app.ld
    -T build/os_symbols.ld     # OS symbol table
    -o build/apps/<name>.elf   \
    apps/<name>/app.c          \
    libs/ui2/*.c               # any library dependencies
    -lgcc
```

Key flags:

| Flag | Purpose |
|------|---------|
| `-nostdlib` | No C runtime -- the firmware provides all needed functions |
| `-ffreestanding` | Freestanding environment, no `main()` expected |
| `-mlongcalls` | Xtensa long calls for arbitrary jump distances |
| `--emit-relocs` | Keep relocation records in the output for runtime patching |
| `-T app.ld` | Linker script setting the base address (0x400D0000) |
| `-T os_symbols.ld` | Resolves OS function calls to firmware addresses |

### Linker Script

The default `apps/app_template/app.ld`:

```
SECTIONS
{
  . = 0x400D0000;
  .text : ALIGN(4) { *(.literal .text .literal.* .text.*) }
  .rodata : ALIGN(4) { *(.rodata .rodata.*) }
  .data : ALIGN(4) { *(.data .data.*) }
  .bss : ALIGN(4) { *(.bss .bss.*) }
  .manifest : ALIGN(4) { KEEP(*(.manifest)) }
}
```

The base address `0x400D0000` is a placeholder. The ELF loader remaps sections to their actual runtime addresses (IROM flash for code, DROM flash for rodata, DRAM for data/bss).

### OS Symbol Table

`build/os_symbols.ld` is generated by `scripts/gen_symtab.sh`, which:

1. Parses `main/os_symtab.c` for lines matching `{"name", function}`
2. Extracts the actual address of each function from the firmware ELF using `nm`
3. Writes a linker script with `PROVIDE(name = 0xADDR);` entries

At link time, these `PROVIDE()` declarations satisfy external symbol references in the app, giving them placeholder addresses. At runtime, the ELF loader re-patches these addresses to match the actual firmware layout.

### Libraries

If an app uses shared libraries from `libs/` (e.g. `libs/ui2/`), create a `deps` file:

```
# apps/<name>/deps
ui2
```

The build script reads this file and adds `-I libs/ui2/` and compiles `libs/ui2/*.c` together with the app.

### Output

The result is a relocatable ELF at `build/apps/<name>.elf`, copied to the SD card as:

```
/sdcard/apps/<name>/program.elf
```

Optionally, a `manifest.cfg` file at the same path controls the app's display name, file associations, and launcher visibility.

## Runtime Loading

Loading an app happens through three layers:

### 1. `os_load_app()` (main/os_core.c)

Called when switching to another app. The sequence:

1. **Checkpoint** the current app by calling its `app_checkpoint()` callback
2. **Unload** the current app:
   - Call `app_close()` to let it clean up
   - `elf_loader_unload()` -- unmap flash, free DRAM
   - `app_heap_reset()` -- zero the 96KB app heap
   - `config_unbind_app()`
3. **Load** the new app via `app_loader_load()`
4. **Save** as `system/last_app` if the manifest says `show_in_launcher=yes`

If called from within an app callback, the switch is **deferred** -- stored as `pending_app_name` and executed at the top of the next event loop iteration.

### 2. `app_loader_load()` (main/app_loader.c)

1. Constructs the path `/sdcard/apps/<name>/program.elf`
2. Calls `elf_loader_load()` to parse and relocate the ELF
3. Resolves the four mandatory entry points from the ELF symbol table:
   - `app_init` -- called after loading
   - `app_event` -- event handler
   - `app_checkpoint` -- state save
   - `app_close` -- cleanup
4. Creates the `app_context_t` with function pointers, subscriptions, etc.
5. Resets the keyboard I2C bus (flash operations can disturb it)
6. Calls `config_bind_app()` to set up the app's config namespace
7. Calls `ctx->init(ctx)` -- first app code execution

### 3. `elf_loader_load()` (main/elf_loader.c) -- The ELF Loader

This is a full ELF parser and runtime relocator. It does the following:

**Step 1: Parse.** Reads the ELF header, section headers, symbol table, and string table from the ELF file.

**Step 2: Find flash partition.** Locates the `app_code` partition (type DATA, subtype DATA_UNDEFINED) and erases it.

**Step 3: Map IROM and DROM.** Calculates code size (executable sections) and rodata size (read-only data sections), then memory-maps them:
- **IROM** (instruction cache): code is mapped via `esp_partition_mmap(ESP_PARTITION_MMAP_INST)`
- **DROM** (data cache): rodata is mapped via `esp_partition_mmap(ESP_PARTITION_MMAP_DATA)`

  This separation is critical on ESP32: reading from IROM with data loads causes a `LoadStoreError`, so code and data must live in different cache regions.

**Step 4: Allocate DRAM.** `.data` and `.bss` sections are allocated from the **app heap** (`app_malloc`/`app_calloc`) in DRAM. `.data` content is copied from the ELF file; `.bss` is zeroed.

**Step 5: Relocate.** For each code and rodata section:
1. Read the raw section data into a temp buffer (allocated from the app heap)
2. Iterate the section's relocation entries and patch addresses

Relocation can target:

| Target | Description |
|--------|-------------|
| **Undefined symbols** | Calls to OS functions (e.g. `display_clear`, `malloc`). Looked up by name in `os_symtab.c`; the address is patched into the code. |
| **Local symbols** | Functions and variables defined within the app. Resolved by finding the section containing the symbol's VMA and computing its offset within that section's runtime load address. |

3. Write the patched buffer to flash via `esp_partition_write()`
4. Apply relocations to DRAM data/bss in-place

**Step 6: Invalidate caches.** `esp_cache_msync()` with `ESP_CACHE_MSYNC_FLAG_INVALIDATE` ensures the CPU sees the newly written code and data.

**Step 7: Resolve entry points.** Scans the symbol table for `app_init`, `app_event`, `app_checkpoint`, `app_close` and converts their VMA-based values to actual runtime addresses.

## Memory Model

### Per-App Heap

Each app gets a **private 96KB heap** allocated from internal DRAM:

```
app_heap_init():
    DRAM  96KB  ┌──────────────────────┐
                │   app heap           │
                │   (multi_heap)       │
                └──────────────────────┘
```

Allocations within an app use `app_malloc`/`app_free`, which operate on this 96KB region. The standard C functions `malloc`, `calloc`, `realloc`, `free`, and `strdup` are all mapped to app-heap-aware implementations through the symbol table.

On app unload, `app_heap_reset()` zeroes the entire 96KB and re-registers the heap, providing strong isolation between apps.

### Memory Layout at Runtime

```
Flash (partition "app_code" ~256KB):
┌──────────────────────┐
│ IROM (code)          │  ← esp_partition_mmap(INST)
│   .text              │
├──────────────────────┤
│ DROM (rodata)        │  ← esp_partition_mmap(DATA)
│   .rodata            │
│   .manifest          │
└──────────────────────┘

DRAM (96KB app heap):
┌──────────────────────┐
│ .data (from app_heap)│  app_malloc'd, content from ELF
├──────────────────────┤
│ .bss  (from app_heap)│  app_calloc'd, zeroed
├──────────────────────┤
│ temp buffers         │  relocation work buffers
├──────────────────────┤
│ runtime allocation   │  malloc/strdup from app code
│   (lines, strings,   │
│    widget trees...)  │
└──────────────────────┘
```

### App Lifecycle Memory Flow

```
Boot:
  app_heap_init()      → allocate 96KB from system DRAM
                         register as multi_heap

Load app A:
  elf_loader_load()    → .data, .bss, temp buffers from app heap
  ctx->init(ctx)       → app's own allocations from app heap

Switch to app B:
  app_checkpoint(A)    → app A saves state via config API
  app_close(A)         → app A cleans up
  elf_loader_unload()  → unbind flash mappings
  app_heap_reset()     → zero 96KB, re-register
  elf_loader_load(B)   → fresh allocations for app B
  ctx->init(ctx)       → app B starts
```

## Symbol Table

The OS symbol table (`main/os_symtab.c`) is a flat array mapping ~385 function names to their addresses:

```c
static const os_symtab_entry_t symtab[] = {
    {"display_clear",      display_clear},
    {"display_draw_text",  display_draw_text},
    {"malloc",             app_malloc},
    {"free",               app_free},
    {"strdup",             strdup_impl},
    {"fopen",              fopen},
    ...
    {NULL, NULL}  // sentinel
};
```

It exports display functions, text mode, input, file I/O, networking, math, Lua, and OS lifecycle functions. Lookup is a linear `strcmp` scan.

At load time, when the ELF loader encounters an undefined symbol reference (like a call to `display_clear`), it calls `os_symtab_lookup("display_clear")` and patches the address. This is the app's only way to communicate with the firmware.

## Manifest System

Each app can have a `/sdcard/apps/<name>/manifest.cfg` with metadata:

```
name=Image Viewer
extensions=jpg,jpeg,png
launcher=yes
```

| Key | Default | Purpose |
|-----|---------|---------|
| `name` | Directory name | Human-readable name for the launcher |
| `extensions` | (empty) | File associations for "open with" |
| `launcher` | `yes` | Whether to show in the launcher UI |

The manifest is also embedded in the ELF as a `.manifest` section at build time (via `xxd -i`), but the current runtime reads it from the SD card file.

## App Lifecycle

### Entry Points

Every app must export these four symbols:

| Function | When called | Purpose |
|----------|-------------|---------|
| `app_init(ctx)` | After loading | Initialize, set event subscriptions, render UI |
| `app_event(ctx, event)` | On event | Handle keyboard, touch, timer events |
| `app_checkpoint(ctx)` | Before switch | Save state (config, position, etc.) |
| `app_close(ctx)` | Before unload | Cleanup resources |

### Event Loop

The main loop (`os_event_loop` in `os_core.c`) polls keyboard, touch, and serial, then dispatches events to the current app:

```
loop:
  if timer_expired && app subscribed to EVENT_TIMER:
    create timer event → app_event(ctx, &event)

  if keyboard_key_pressed:
    create keyboard event → app_event(ctx, &event)
    check for Ctrl+ESC → switch to launcher

  if pending_app_switch:
    execute the deferred app switch
```

### App Switching

When `os_load_app()` is called (e.g. from the launcher or from within an app):

```
1. app_checkpoint(current)     → save state (to SD card config)
2. app_close(current)          → cleanup
3. elf_loader_unload(current)  → unmap flash, free DRAM
4. app_heap_reset()            → zero 96KB app heap
5. elf_loader_load(new)        → parse, relocate, allocate
6. keyboard I2C recovery
7. config_bind_app(new_name)
8. app_init(ctx)               → app starts
```

The app heap is zeroed between apps, providing complete memory isolation.

---

## Key Constraints

- **SD card required** -- the firmware halts if it cannot mount `/sdcard`
- **App heap limited to 96KB** -- apps must be memory-conscious
- **No C runtime** -- no `main()`, no global constructors, no `atexit`
- **Static ELF loading** -- apps are fully loaded and relocated before `app_init` is called; no lazy binding
- **Flash write endurance** -- the `app_code` flash partition is erased and rewritten on every app load
